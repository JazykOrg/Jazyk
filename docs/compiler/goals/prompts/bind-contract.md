Bind ONE requirement to the deliverable. Steps: 1) Search the deliverable for an implementation of the statement; record the carrying files, or none. Absence is a finding, not a failure. A file that only restates the statement (a page repeating the sentence, a comment) does not carry it: list the files a criterion test inspects, and none when no such file exists, so the row reads unimplemented and generation opens rather than failing. 2) Search for an existing test that judges the statement, starting with the package's existingTests (the files that name this requirement by id, slug, or hash); bind to it when found, never write a duplicate beside it. A test carrying this statement's hash (in its name or its marker comment) under another requirement id is this requirement's test, since ids renumber between compiles while the hash follows the statement: rename it to the suggested name and bind to it, never write a second one beside it. A test named with this id but another hash belongs to whatever statement that hash names now, not to this one. 3) When a criterion has no test, write one: the package's criteria are the evidence the requirement is met, one test per criterion named by its suggestedTestName, and a requirement without criteria takes one test on the statement. Implementation found: the test pins the observed behavior. Implementation absent: the test encodes the criterion and fails by design; it is the acceptance gate generation must clear, so it must be a test some implementation can pass: assert the refusal or outcome the criterion states (a constructor returning an error, a validity check answering false, a message), never a contradiction of the input you passed (asserting that an order built from no items has items can never pass). 4) Run the tests and record the binding with record_binding: files (empty list when nothing implements it), tests (one entry per criterion with its verdict and evidence; the requirement-level test only when there are no criteria), the verdict, the evidence. One file per requirement may hold every criterion's test; each entry's run command must then select its own test by name (cargo test <name>, npx tsx --test --test-name-pattern <name>, python3 tests/<file>.py <name>), since a run that executes the whole file judges every criterion at once. The row's status then reads verified, unimplemented, partial (files exist and the criterion tests split: generation work for the failing ones), or failing (every test fails against existing files: a finding for the author). The test must be falsifiable (its assertion fails when the requirement is violated) and inspect the artifact, never prose about it; one that asserts the source text contains words or module names inspects prose, not the artifact, and is the llm case or a real behavioral assertion; so does one that reads a constant, an object literal, or a table describing the artifact (endpoint paths, a runtime or framework name), which is a description in another syntax: the test drives the artifact (starts the server and calls the endpoint, runs the command, opens the output), and a file holding only such a description implements nothing. Use the suggested test name. A requirement with no falsifiable programmatic assertion binds a kind llm test: write the criteria file and record it with verdict from your own judgment of the deliverable. Never rewrite implementation files during binding; binding observes, generation changes.
