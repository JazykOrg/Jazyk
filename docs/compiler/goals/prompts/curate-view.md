This goal decides membership for one view against the nodes the harness matched to it: new entities matching a structural view's query, or a behavior requirement the flow placement check found in no flow view and matched to this one by its actor and its document (a failure-mode statement represented in no branch arrives the same way). Load the view in full and each matched node; the skill for the view's kind (structural-views for class, object, package, component, composite, and deployment; flow-views for use case, activity, sequence, communication, and overview) says what belongs. Decide every matched node exactly one way: add it with update_view add_members, or exclude it with update_view exclude and a note naming the sentence or the rule that keeps it out ("constraint, not flow", "example, not flow", "belongs to view:usecase/returns"); the note lives on the view and is what the next build reads, so a bare exclusion is not a decision. In a flow view, place an added member at its position in the flow: the default order is document order of the members, and you reorder only when the documents state the order (a "then", a numbered step, a trigger chain where one member's receiver acts as the next member's initiator, a state the next step requires), naming the ordering sentence in the justification; a failure-mode member sits immediately after the step whose failure it handles, and a statement that belongs to another intent is that flow's member: add it to that flow in the same session, creating a use-case view with upsert_view when no flow carries its intent, and exclude it here with a note naming that flow. In a structural view, an added member brings every relationship among the members by itself, and an arrow you miss is a missing edge (declare-edges work), never something the view adds; a match that belongs to another view is excluded with a note saying which, and a query that matches wrongly is narrowed (scope, parent, stereotype, depth) rather than replaced by a list. Retitle with update_view when the derived title reads as a fragment. Never invent a member the documents do not state, never delete a default view (exclude or collapse instead), and never satisfy a limit here by dropping members: a view the decision pushes over its limit derives split-view at commit. Editing a default view makes it curated, and its derived members keep arriving. The gate: every matched node is a member of the view or is excluded with a note on the view, and mark_goal_done carries in evidence one verdict per matched node, added or excluded.
