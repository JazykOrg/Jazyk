This goal writes the acceptance criteria of one entity's requirements: for each requirement the change lists, the observable evidence that it is met, one condition and its outcome per criterion, concrete values kept, written from outside the system (what an observer sees, never a function, a table, or a file). Apply the criteria skill: read the requirement's statement and quote, then its section and the Examples or Test cases sections the hints name; link existing supporting prose with upsert_criterion carrying section and verbatim quote, including descriptive text and the requirement's own quote when it states the whole observable condition and outcome; observer wording alone does not make a criterion derived. Do not add a paragraph restating an existing title, appearance, content, or behavior description. The quote need not use the criterion's wording, but must support every value and obligation; where the documents state nothing, write derived criteria with provenance derived from the requirement and reasoning, each a sentence the documents should gain. Cover the boundary of every bound, the negative case of every conditional, the measure of every quality facet; never restate the requirement as its own criterion, and never invent a value the documents do not give: that is an invented-choice prompt naming the requirement, and the requirement's verdict is open-question when no criterion can be written without the value, or complete when the criteria that need no value still cover the shape (file the prompt either way). The gate: mark_goal_done carries evidence {requirements: [{id, criteria: [ids], verdict}]}, one entry per listed requirement with its criteria and a verdict: complete when the criteria now cover the requirement's shape (its bound, its negative, its measure), whether derived or stated; stated-only when the documents' own criteria already cover it and you added none; open-question when a value nobody stated keeps a criterion from being written, no criterion restating the statement, and every derived criterion carrying from, reasoning, and a definition-grade sentence for the docs.
Read existing criteria and pending proposals before adding another. Reuse or update the same condition and outcome. Combine evidence checks of one outcome; do not split each configuration key into a separate proposal. Keep independent outcomes separate. A derived statement must read as useful documentation, with the actor, condition, and observed result understandable without graph ids. Do not invent failure behavior from an absent setting.
Read every stale criterion against the revised requirement. Refresh one that still applies with update_criterion using its id and current or corrected statement, even if its wording stays the same; otherwise replace or delete it. Merely citing an existing stale criterion does not refresh it. No verdict, including open-question, may leave a stale criterion on the requirement.
