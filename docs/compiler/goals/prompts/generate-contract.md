Generate the entity's part of the deliverable AND the tests for its requirements.
- The opening batch may assign several entities. Keep track of each assigned entity and record its generation before finishing the batch. begin_generation inspects one package; it does not complete the other assigned entities. A testing component does not replace the tests required for the components whose behavior they check. Finish meaningful source changes before running their checks. Human steering can refer to the whole workflow, including earlier workers. Acknowledge the requested change before continuing. Do not deny earlier test runs merely because they are absent from this worker's history. When the user asks about activity outside this worker, inspect task_context and its recent runs as needed before answering.
- Reuse the medium the package records. If it is undecided, choose from the documents and call record_medium before writing. Never re-decide a recorded medium. You choose only the layout, the file names, and the build or support files that make your recorded commands executable; every file you write must appear in the manifest you record when the goal is done.
- The deliverable is the artifact itself, never a description of it. A requirement naming a format, a medium, or a piece of content is an obligation to PRODUCE that thing. Writing a document that says the artifact will be in some format, or a manifest listing what the artifact would contain, satisfies nothing. When the medium is text the requirements describe directly (source code, a manuscript, a configuration), your files are the deliverable. When the medium must be produced by a tool (a slide deck, a PDF, a rendered site, a compiled binary, an image), write the source that produces it and return a `build` in the manifest: {run, cwd, produces} where `run` names `task:<id>` for an isolated build and `produces` lists deliverable-relative artifact paths. The task cwd and product globs are project-relative. The harness runs the build before any test. One build per deliverable: if the package already carries a `build`, reuse it and extend its source instead of recording a second one.
- Content requirements are satisfied by content. A requirement saying the artifact shows a title, states a definition, or uses a color is met only when the artifact carries that exact title, that definition, that color value. Never write placeholder filler (`[Project Goal]`, `Lorem ipsum`, `TODO`) in place of what a requirement states. If a requirement does not say what the content is, implement exactly what it does say and nothing more.
- Inspect referencedAssets in the package. These are the exact local inputs named by quoted facts, with project-relative paths, source references, status and SHA-256 digests. Read and use the supplied input. Preserve its appearance and content instead of drawing a replacement or inventing a placeholder. Reuse its path when the product can read it, or copy its exact bytes into an allowed Source path when the layout needs a product-local asset. Use existing file tools for text such as SVG, or a saved project task to copy binary files from the project snapshot. List a task you rely on beyond tests and the build under manifest.tasks; an unlisted task you added is removed once nothing uses it. Output references name generated files and do not supply input bytes. A missing, unreadable or blocked input must be reported and resolved before recording generation; never substitute an invented asset. Source and Documents write boundaries still apply.
- When a quote asks you to create a linked output, such as Home/index.html, declare its intended project path in Source through the existing scoped matcher tools before recording. Then reload begin_generation for the current package and factHash. Supplied input assets must stay inputs; never reclassify one as Source to bypass a missing, unreadable or unsafe input.
- Inspect task_context, dependency manifests, runner configuration and existing test commands before defining execution. Reuse ordinary project tasks such as test, test-unit or test-browser. Extend their discoverable suites so adding a criterion does not require another task or a saved command edit. Requirement and criterion ids identify test cases, not runtime environments. Separate suites are appropriate for different toolchains, isolation needs or independently useful project operations.
- One toolchain per deliverable: the run commands already recorded (the package lists them) establish the language, the test runner, and the command style; reuse them exactly. Never introduce a second test runner.
- Exclusive deliverable files belong to one entity or its component group: a file a sharedWith member recorded you may extend and record too. Never overwrite another group's exclusive module; import or link it instead. Redefining its type is the same violation. Support files belong to the deliverable and every entity may extend them while preserving existing parts: package.json, Cargo.toml, a crate root, a package's __init__, or a shared composition page when written files are the artifact. The package lists recorded supportFiles. List support under manifest.supportFiles, and also under files when it implements your requirements.
- A legitimate shared entrypoint may have been recorded first by another group. Explicitly promote it before editing: call begin_generation for its recorded owner, preserve its content and the owner's current files and tests, and record_generation with the entrypoint added to manifest.supportFiles. Then begin_generation for your entity again, read and extend the shared file, and record it in files for your requirements. This is not permission to take over an exclusive module or discard another entity's work. No filename is automatically shared. Source and Documents boundaries still apply.
- Paths are relative to the deliverable directory, never prefixed with its own name: when the deliverable is `handbook`, a page is `hiring.md`, not `handbook/hiring.md`.
- Record the files that realize your requirements under manifest.files. Test and criteria files are not implementation: a record whose files hold nothing else is refused while a requirement of yours has no row naming a file that realizes it. A requirement a file of another entity already carries (a page or a module you may not write) is recorded by naming that file on the requirement's test row (`files: [path]`). Only an entity whose every requirement is carried by another entity's files records files: [].
- Use `task:<id>` for programmatic runs. Set the task cwd relative to the project; for a deliverable under `deliverable/`, use cwd `deliverable` and report globs such as `deliverable/reports/*.xml`. Manifest artifact paths remain deliverable-relative. Legacy shell commands execute from the deliverable directory. If it needs a build or configuration file that no goal has written yet (package.json, Cargo.toml), write it and list it under manifest.supportFiles.
- A dependency manifest you write or extend (package.json, Cargo.toml, pyproject.toml, requirements.txt) pins each dependency to a version you resolved: a caret or exact range on a version that exists (`^4.19.2`, `=1.0.3`; ask the registry when unsure, `npm view express version`), never `latest`, `*`, or an empty range, since a manifest that says `latest` installs a different program on every install and the tests that passed here say nothing about it. Name the package or module for the deliverable or the entity that owns it, never for one part of it: a package that holds the backend beside the frontend is not `frontend`. The deliverable has one entry point, the file the manifest's `main` or `scripts.start` names; it is a support file, so extend the one that exists instead of writing a second one beside it. A second file that repeats the first's role (two servers, each requiring the framework and opening the database) is a defect, not a layout choice: keep one and delete the other before you record.
- Every requirement is an obligation; implement each and place a single-line marker comment directly above the implementing site: `req:<id> hash:<hash8>` in the medium's comment syntax, nothing else on that line. The id already begins with `req:`: for req:orders-4 write `req:orders-4 hash:29f2c263` and nothing more, never `req:req:orders-4` and never the quote or any other text after the hash. The harness strips marker lines from your files and records each location in the ledger, so the delivered file stays clean.
- A current binding comes from boundTests, not suggestedTestName. Reuse its exact requirement and criterion ids, artifact, kind and selector, including any classname::name prefix. Resolve paths from the current deliverable root and sourceSelection; never strip a directory named deliverable by convention. After compaction or a manifest refusal, reload begin_generation if any package field is missing or uncertain before another recording call. Keep completed writes and evidence; do not repeat them just to reload a package.
- A prescribed layout is an obligation alongside its content. Test complete ordered groups, such as the exact three paragraph texts, rather than a count plus independent sentence matches. If the graph omits that obligation, report it for guarded reconciliation; do not treat a passing content test as layout coverage.
- Develop the actual implementation and its tests together. Choose their order. You may write source before tests or execution, then inspect, test, and refine it. A separate binding pass and a failing baseline are not prerequisites. The package's boundTests lists existing rows with their criteriaTests. Inspect each existing test against its documented obligation. Reuse valid test artifacts, selectors, kinds, and assertions. Correct undocumented implementation assumptions, such as requiring CloudFormation JSON when the documents require only CloudFront and S3, while preserving assertions of required behavior. Explain each correction and the obligation it still checks in the session summary. Changed tests need fresh evidence. Never weaken a required check to force a pass or write a duplicate beside it. A stale statement or criterion needs a test for its current obligation. For each missing criterion test, create one named by its suggestedTestName and include requirement and criterion in manifest.tests. - Reuse a saved suite task across related requirements and criteria, with a distinct JUnit selector per test. Existing tests may change run and cwd to that shared task, keeping artifact, selector, kind, and assertions. New routing clears old evidence and must emit each exact selector again. Run it when meaningful source exists. Do not allocate a separate task or container per requirement or criterion by default. Test functions can share files across requirements. The suite command runs them together and exact JUnit selectors retain independent verdicts. run_tests groups the related selected targets by saved task. Repeating run_tests for each criterion would start fresh runs of the same suite; choose useful execution milestones instead. Recording a test declaration supplies no verdict; run_tests supplies programmatic evidence against the current implementation.
- Choose programmatic tests for executable behavior: command output, exit status, API responses, and generated artifact contents that can be inspected automatically. The presence of criteriaPath only supplies a path if judgment is needed; it does not recommend an LLM test. A missing test runner is setup work: reuse or define a saved task and a runner that emits JUnit cases. Never substitute a written PASS for an execution result.
- An llm criteria artifact is Markdown with YAML front matter naming requirement and hash (also criterion for a criterion test), followed by inspection steps and explicit PASS and FAIL outcomes. Use the package's criteriaFrontMatter. Write it under an allowed source path; update_document_set can add its Markdown path to set.source using baseHash from list_document_sets while preserving the set id, docs, roots and unrelated source patterns. An executable test source cannot substitute for this file.
- programmatic: any test a command can run (unit, integration, cucumber are examples, not a taxonomy). Each manifest.tests row must carry requirement, criterion when it tests a criterion, kind, label, artifact, name, and run. artifact is the deliverable-relative test source containing the declared name (e.g. tests/test_greeter.py), never the generated JUnit XML. Keep the report path only in the saved task's reports globs. Never hand-write a report to satisfy a manifest gate. Write the test into the deliverable and bind it with run="task:<id>" and name equal to its exact JUnit classname::name (or a unique case name). Several tests may share the task; each verdict comes from its own fresh report case. Legacy shell bindings select only that test and use its exit code as the verdict. The test command must propagate failure: a harness that prints a failure and still exits zero verifies nothing. The test must inspect the artifact the requirement is about, never a document that describes it: asserting that a manifest names a format or that a plan lists a feature is circular, since both sides are your own prose. A test that asserts the implementation source contains words, names, or module declarations inspects prose about the artifact, not the artifact: that is the llm case, or a real behavioral assertion. When a build produces the artifact, open what the build produced. A test must run with no fixture the deliverable does not define; if it needs setup, write that setup file and list it in the manifest. The test must be falsifiable: its assertion has to fail when the requirement is violated. If the only assertion you can write would pass either way, the requirement is not programmatically testable from this artifact; declare it llm instead of writing a test that always passes.
- llm: the requirement needs human-like judgment that an executable assertion cannot establish. Non-software artifacts can still have programmatic checks for their structure, contents, or format. Write a criteria file (the package names its path): front matter with the requirement id and statement hash, then the statement, the quote, the implementing file paths, the steps to confirm, and the verdict contract (PASS or FAIL plus reasoning).
- Name a test you write with the name the package gives it: a criterion's suggestedTestName (crit, slug, hash prefix), or the requirement's testName (requirement id plus hash prefix) only when it has no criteria; put the single-line marker comment above it.
- Reference other entities' files through the manifest the package carries.
- Dense entities generate in parts of {GROUP} requirements: part 1 is the core plus the first group; each later part receives what exists so far and returns ONLY additional content to append.
- Write a long file in parts when your tool calls have a size cap: write_text_file for the head, then the rest with append: true, each call a few thousand characters at most; a call cut mid-way lands nothing.
- Return only file content, never fences or prose, when asked for a file.
