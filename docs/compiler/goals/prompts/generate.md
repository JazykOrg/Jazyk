This goal produces one entity's part of the deliverable and the tests for its requirements, then records the manifest. Claim the entity with begin_generation, as the pointer line among the hints says for this target: its reply carries the generation contract as instructions (the deliverable is the artifact and never a description of it, one toolchain per deliverable, file ownership, marker lines, one test per requirement in one of the two kinds, dense entities in parts) and the package (the entity and where its files go, the factHash to pass back, the medium, the recorded build, the run commands already established, the requirement ids that changed, other entities' files with what each holds, the tests binding already wrote, the requirement groups with each testName, statement, and quote, the entity's neighborhood); follow that contract exactly. Read the package first: the medium decision in it is already made, never re-decide it, and list_files and read_text_file show what exists. Write your files with write_text_file, paths relative to the deliverable; several files are normal (source, tests, support files). Never write to another entity's file, reference it through imports instead; a path another entity owns is rejected with the owner named. Make it real: when the package names a build, extend its source and run it with run_command, never recording a second build; when your test commands need a runner or a configuration file that does not exist, write it and list it in the manifest; run_command shows exit codes and failures, so fix your work until the commands you will record actually succeed. Make the bound tests pass without changing them: a bound test you cannot make pass is left untouched and named in your justification, its row reads failing, and the repair is a human's decision (re-bind, or fix the documents), never a quiet rewrite of the judge. Content requirements are satisfied by the exact content the statements name, never placeholders. Anything the deliverable needs that the documents do not state is a choice: make it with best judgment, implement it, and name it in the choices argument of record_generation, beside the manifest, each entry carrying the scope of what you had to invent (product, behavior, or detail), a message stating the choice, and the requirements it serves when any, so the harness files it as an invented-choice diagnostic graded by scope and the documents gain a proposal; never stall on one and never hide one. A test is falsifiable (its assertion fails when the requirement is violated) and inspects the artifact, or what the build produced, never prose about it; a requirement with no falsifiable programmatic assertion is declared kind llm in the manifest with a criteria file at the path the package names. Marker lines (req:<id> hash:<hash8> in the medium's comment syntax, alone on a line, directly above the implementing site) are stripped at record time and become anchored traceability sites. Record with record_generation: the manifest lists every file you wrote, one test row per requirement, and the build when the medium is built, and choices beside it lists what you invented; it rejects a programmatic row with an empty artifact or run, a declared test name absent from its artifact, and a built medium with no build recorded. Then run_tests verifies the programmatic rows, the build first, once. Fail the goal when the medium cannot be produced (no toolchain available, a build that cannot run). The harness checks the ledger, not your word: a session that never called record_generation has failed the goal. The gate: record_generation landed for the entity with a factHash equal to the live graph's, and run_tests ran afterwards; then mark_goal_done with a one-line justification, and done.
