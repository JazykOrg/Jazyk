This goal judges one entity whose fact set changed: load it in full and read its requirements, gathered across all documents, as a whole, with the judgment skill. Refresh the definition with update_entity when it fails to match the statements as a whole, and treat stereotype and parent the same way, changing them only when the statements support the change; never reword a definition that still fits. A composition edge whose part has no parent is unfinished work: a stated composition is that support, so set parent on the part (the edge's b) with update_entity. Judge every lookalike the hints list: a name variant ("backend" and "backend system") or a synonym is the same concept, so merge with merge_entities (keep the better-established id) and say why; a field, part, state, role, threshold, instance, or child concept is a separate entity when statements are directly about it ("Product price" is not a variant of "Product"), a shared word proves nothing ("Reorder point" is not "Order"), and where the statements state the whole-part the move is parent, not a merge. When a listed statement names this entity without referencing it and is about it, add the entity with update_requirement passing only id and entities (the full list, including the ones already there); about it means the statement constrains, changes, or produces this entity (its existence, its state, its content, its value), not that it names the entity as the place, the means, or the condition of another entity's action: "A Customer pays for an Order through Payment" is about the Order (it gets paid) and references it, while "When the Stock of a Product reaches zero, the Catalog hides the Product" only reads the Stock as its condition and does not reference it, and "Orderly returns it to the warehouse" under Returns is the verb, not the area; never pass section or quote on such a call, they re-anchor the provenance to another sentence, and a missing reference is what strands an entity unreachable. When two requirements on this entity state the same obligation reworded and quote the same document, keep the better-sourced one and delete_requirement the other, saying why (a lead-in sentence's requirement restating its list items is the common case); when they quote different documents, keep both and report_diagnostic rule duplicate-requirement, severity info. File real problems with report_diagnostic: contradiction for requirements that cannot all hold, duplicate-entity for two entities that are one concept when a merge is not certain, ambiguity for a statement open to more than one reading, missing-link for a concept the documents rely on but never define (a relative link to a missing file is the broken-link check's finding; never refile it), lint for a project lint rule violated inside a source quote, with a prompt carrying the one suggested edit when the correction is obvious. A multi-entity statement without edges has its own declare-edges goal (the hints list them): leave the edges to it, and add edges here only when a merge or a reference you staged changed what the statement ties, with update_requirement passing only id and edges, each with a type; a statement that names the other entity only as a condition or trigger ("if the Product is out of stock") ties nothing and gets no edge. A part several wholes compose in one statement ("Every employee belongs to exactly one department" beside four departments) takes none of them as parent: the whole-part is aggregation, or a generalization the members instantiate, and the part stays where its own sentence puts it. An open diagnostic whose condition has lapsed is resolved with resolve_diagnostic; one naming a subject marked (deleted) cannot stand as filed, so resolve it and refile against the surviving statements when the finding stands. Documentation is loose by design: flag only findings the author can act on, never formal-spec completeness (persistence details, versioning, exhaustive cases); severity error only when two statements cannot both hold, warning for real but repairable issues, info for observations. A wrong merge or delete destroys information; a missed duplicate only leaves a finding; when in doubt, keep both and file. When everything is coherent, mark the goal done with no mutation. The gate: mark_goal_done carries evidence {definition: current | refreshed, lookalikes: [{id, verdict: merged | separate, reason}], diagnostics: [{id, verdict: stands | resolved | refiled}]} and the staged work matches it: refreshed requires a staged update_entity with definition on this entity and current requires none; one entry per listed lookalike, merged backed by a staged merge_entities naming it, separate carrying its reason on the entry (or an open duplicate-entity diagnostic naming both when the merge is not certain); one entry per diagnostic the goal's hints list as open on the entity or its statements (open when the batch was claimed; a diagnostic staged in this batch, not yet committed, is the filing goal's evidence and needs no entry here; one committed by an earlier batch is open and listed like any other), resolved backed by a staged resolve_diagnostic, refiled backed by that resolve plus the new report_diagnostic, and a diagnostic with a deleted subject cannot stand.
