Extraction is how a section becomes graph: statements first, entities only as statements need them, quotes verbatim, edges and facets as judgments beside each statement, and one honest coverage mark at the end. The documents may describe software, a slide deck, an organization, a novel, a contract, a course. The subject is whatever they describe and its parts, and every rule below reads the same in every medium.

The sentence test. For every sentence, ask: does it say what the subject or one of its parts is, does, contains, shows, uses, allows, requires, or limits? If yes, it is a requirement. Documentation rarely says "shall": write the obligation as a `statement` in clear wording of your own, in the documents' terms, and keep the source sentence verbatim as the `quote`. "The system" in a document is a placeholder for the real subject, never an entity: mint no `System` or `Order System`; reference the entity the sentence means.
- Content, appearance, format, and material facts pass the test and are the most often missed: what an artifact says, shows, or contains is an obligation on it, and a stated value, color, font, size, or measurement is an obligation on the thing it describes. "The primary color is #248555" yields "The slides use #248555 as the primary color."
- Composition and technology choice pass the test: "The gateway is a REST service built with Go" yields two requirements, both quoting that one sentence.
- Access and permission rules pass the test: "All management operations can be performed by Admins only" yields "The user management system allows only Admins to perform management operations."
- Navigation does not: a sentence whose only content is where something is written ("The slides are defined under slides.md", "This document describes how the gateway works") constrains the documentation, not the result. Skip it. A sentence that assigns a part or a responsibility through a link ("The warehouse side is covered by [Inventory]") states a fact about the subject, not navigation: extract it. Only a sentence whose sole content is where prose lives is navigation.
- History does not: a sentence reporting a completed past event ("Ridgeline hired its first recruiter in 2019") states no obligation on the subject today. Extract only the standing rules such prose hides, cover the section on those, and mint no entity mentioned only in history.
- Extract only what the source states. Never invent a fact the text does not carry. A stated fact is never "just a fact": the document states it because the result must match it.

Granularity is judgment, not arithmetic. Split what can fail independently; keep together what one check verifies ("Uploads accept PNG, JPEG, and GIF" is one requirement with three values). One honest test name per requirement is the right density; no count is a goal. A statement carries one obligation and is never a paragraph. Keep the trigger before the response when the sentence has one, keep the concrete values and conditions, and keep literal identifiers verbatim, backticks included: binding searches code by the statement text, and a paraphrase that drops `addProduct` breaks the link.

Enumerations. A sentence ending in a colon followed by a list is a claim about the items; the lead-in alone states nothing the items do not.
- An item with its own verb or description is its own requirement, quoting that single bullet line verbatim. An operations list is the common case: each operation is separately built and tested.
- Items share one requirement only when they are plain values with no behavior of their own (accepted formats, supported locales): quote the lead-in line and carry the values in the statement.
- An item naming an actor, a component, or a sub-system introduces that entity, and the lead-in's subject is the whole: an entity too, minted if absent. Record each item's requirement with both entities, a `composition` edge from the whole to the part, and the part's `parent` set to the whole. An item that is a link still counts: under "The sub-systems are:", the item `[User Management](./user.md)` states that the whole includes User Management. The link is navigation; the item's text is a fact.

Code blocks. Pseudo code, step lists, and algorithm sketches are claims about the subject, step by step: one requirement per step that states behavior, quoting that step's own line. A branch is its own obligation ("If the stripped line is empty, continue to the next line" is a failure-mode requirement). A variable local to the steps (a counter, an accumulator) is requirement detail, never an entity. A block is an illustration only when it shows sample data, an outside system's output, or a payload format. The section is covered only when each behavioral step has a requirement; extracting one step and skipping the rest is a dishonest claim. A PlantUML block is a diagram section and states obligations the same way: each element and each arrow is a claim about the subject.

Test cases. A case with concrete input and expected output is a triggered obligation on the system under test: quote the case's lead-in line and carry the values in the statement ("Given the input lines `321`, `654`, `453`, the sort utility outputs `321`, `453`, `654`."). Reference the entity under test, never the test file or the suite. A test-case section is never non-normative.

Quotes. Copy the quote character for character from the section body loaded for you: for a list item, that one bullet line; for a step, that one line. Never paraphrase, merge, or reflow a quote. A quote that is not in the section is rejected. The sentences in this skill are illustrations, never content: extract only from the loaded bodies.

Entities are the subject's own parts, actors, and domain objects: a component, a type, a role, a stored record, a product, a slide, a chapter, a character, a department. Never file paths, flags, markdown constructs, generic phrases, operation names, or technologies (React, Go, PostgreSQL belong in the statement text). The document itself (a glossary, an overview, a roadmap) is not an entity. A tool, store, or place named only as the channel or location of an action ("filed on form EX-12 in the expense tool", "stored under a shared drive path") is requirement detail on the acting entity, never an entity.
- Search before you create. Call `search` for every entity a statement needs. Reuse the entity that means the same concept under any wording ("backend", "backend system", and "the Warehouse backend" are one entity) and record the new wording with `update_entity` `add_aliases`. Create with `upsert_entity` only when search finds nothing that means the same thing. Tools take ids, never display names.
- A plural that names an area and the singular that names the thing are two concepts: a front door listing Orders, Shipping, and Platform names areas, and a section stating "An Order is a customer's request" names the concept under the Orders area, its `parent`, never an alias of it. Reuse the area for the area and mint the concept beneath it.
- One sentence introduces at most one entity for its subject: "This software is a warehouse management system" defines one entity, the second wording an alias.
- A pronoun subject (this, it) resolves to the subject the document already introduced; never mint a new entity from the predicate noun. When the loaded set names the entity another document introduced for this one, "the system" is that entity, and its statements reference it.
- Never substitute a broader system for a named part: "The inventory system manages products" is about the inventory system, not the application containing it.
- When the grammatical subject is barred from being an entity (a flag, a path, a command, a value), attach the requirement to the owning entity in scope: "The flags `--verbose` and `--quiet` control logging" is a requirement on the CLI.
- Anything a statement merely mentions (a field, a threshold, a value, an operation) is requirement detail carried in the statement; mint a sub-entity only when statements are about it directly.
- Never set `scope` unless the documents explicitly name a bounded context; an invented scope splits one concept into two.
- Supply `parent` on `upsert_entity` when the section states the whole the entity belongs to. Two same-named entities under different parents are two concepts (a `Config` in each module); an upsert without `parent` that matches several is rejected naming the candidates, and the repair is to pass `parent`.
- A `stereotype` is your judgment of what the medium calls the concept (system, service, interface, actor, slide, department, character), recorded only when the section supports it: the sentence says what kind of thing the concept is ("Orderly is an online shop system", "Operations, the department that"), or the concept acts as that kind (an actor performs the action). A concept the section only names and uses (the Order, Payment, and Shipment of "places an Order, pays through Payment, and receives a Shipment") carries no stereotype: leave the field absent. `component`, `entity`, and `class` are never defaults; a label the documents do not support is an invented fact, and a structural label (`system`, `component`, `service`, `interface`, `actor`) on one child turns its whole level's diagram into a component view. `system` (a level holding a system renders as a component view), `actor` (flow clustering and use-case actors), and `interface` (the provider check, sequence receivers) carry meaning for derivation; `interface` means a contract something realizes, and a CLI, GUI, or tool is never one; every other label is text the renderer shows.

Subjects and references. Tag each requirement with the entity the statement is about (its own grammatical subject) and every other entity the statement names. Multi-entity statements are what makes the graph a graph.

Edges. When a statement ties two entities structurally, declare the pair in `edges`, directional (`a` acts on `b`) and typed: the whole is `a` of a `composition` or an `aggregation` (a belongs-to sentence makes the container `a`), the realizer `a` of a `realization`, the instance `a` of an `instantiation`, the dependent `a` of a `dependency`, the specific `a` of a `generalization`; `association` for a plain link, `aggregation` for a shared part. Composition claims exclusive ownership: one whole, and the part's `parent` follows it. When the part is shared across wholes or listed by several ("Orders contain Products from the Catalog"), the type is `aggregation`. Always state the type: an edge without one counts as the weakest, `dependency`. Add `cardinality` (`1`, `0..1`, `1..*`, `*`) when the sentence states a count ("holds one or more order items" is `1..*`). One sentence, several arrows: "A calls B's endpoint" yields `A→endpoint` and `A→B`, both `dependency`. Both ends of every edge are in `entities`. A sub-system list is the common case: each part ties to its whole.
- When a goal asks for edges on a multi-entity statement that has none, declare them when the statement ties the entities structurally. When it only names them in passing ("the report lists orders and customers"), declare none and say in the justification that the statement is not structural.

Transitions. When a sentence describes a state change ("When payment succeeds, the order becomes paid"), record `transition: {subject, from, to, trigger?, guard?}` beside the statement; the subject is in `entities`, and it is the entity whose documented lifecycle changes, never an entity another component shows or hides ("the Catalog shall hide the Product" is the Catalog's display behavior, not a Product lifecycle). "Marks the X as paid", "puts the X on hold", "X becomes S", and "cancels the X" all state a change into that state. The event is the `trigger`; a count or deadline condition is the `guard`: "Payment fails three times" is trigger `Payment fails` with guard `three times`, and "not paid within 21 days of placement" is trigger `not paid` with guard `21 days after placement`. The event that creates the subject names its initial state: placement puts an Order in `placed`, so "not paid within 21 days of placement" leaves `from: placed`. State names come from the documents, never invented: a state name is a stage word the documents use for the subject, an "either A or B" outcome is two transitions and never a compound state name, and two sentences moving the subject between the same `from` and `to` restate one transition, recorded beside the sentence that states it directly. Only when a sentence names the state entered and no sentence, creation event included, places the subject anywhere before it, record no transition, since a machine with an invented state is worse than none.

Attributes. When a sentence states structure ("An order carries a total and a currency"), record the requirement on the entity and add the named attributes with `type` where the sentence states it, each quoting that sentence. When a sentence is a worked example ("Ana, a gold-tier customer, keeps 3 items in her cart"), it introduces an instance: an entity with `value` on its attributes, tied to its type by an `instantiation` edge on the requirement that states the example, with `association` edges for the links the example states. A worked example under an Examples or illustration heading whose values nothing else uses is illustration, not an instance: extract only a rule no other section states and mint nothing; its incidental values (a day of week, a name, a quantity) are illustration detail, never a statement, and a sentence in an example section never records a transition. A form number, filing label, or path a sentence names stays requirement detail in the statement, never an attribute, and a document's own numbering scheme mints neither entity nor attribute. Behavior is never an attribute; it is a requirement.

Facets. Record each statement's facets with one line of reasoning each: `behavior` (the subject does something, on an event or as a step), `constraint` (an invariant the subject holds), `failure-mode` (what happens when something goes wrong), `quality` (performance, capacity, availability; `measure` carries the stated bound only when it is a number, duration, count, or rate, e.g. `2 seconds`; a bare adverb like promptly or quickly is the unmeasured case, so leave `measure` absent and let the check surface the gap). A statement may carry several facets or none. A transition statement usually carries `behavior`; a branch handling bad input carries `failure-mode`.

Stale anchors. A stale anchor is a requirement whose quote fails to locate in its section. It has three outcomes: the document still states the fact, so re-record it with `upsert_requirement` and a fresh verbatim quote (the same statement updates it in place, and the id survives); the fact changed, so revise it with `update_requirement` carrying the new statement and quote; the fact is gone, so `delete_requirement` with a reason. An untouched stale anchor parks the goal.

Stability. Prefer a no-op over cosmetic rewording; the graph's stability across builds matters more than polish. A statement already extracted and still made by the section is left alone. Reword an existing requirement with `update_requirement` on its id, never with a second upsert. A call that only adds entities or edges to a requirement passes only `id` and that field, never `section` or `quote`, which re-anchor the provenance.

Rounds. A section's extraction is a few replies, not a reply per statement: one `search` with `queries` for every name the section introduces, then every `upsert_requirement` and `upsert_entity` the section yields in one reply, then `set_coverage` with the goal mark; only a call whose arguments need an earlier reply (the id a search returned, a section you have not read) waits a round.

Coverage honesty. After a section's extraction, call `set_coverage` exactly once: `covered` when a requirement sourced from it is staged or recorded. `non-normative` is the exception, allowed only when no sentence passed the test: navigation that only links elsewhere, a glossary that only defines outside terms, a changelog, a roadmap wish list; give a real note. A glossary entry that states what a part does is a requirement wearing a glossary's clothes; extract it. The counterweight: an entry that only fixes vocabulary ("X is the term for Y") states no obligation and mints no entity, and a section that declares itself non-authoritative while its facts are owned by other pages is the non-normative case; definitions the owning pages already state are not extracted twice. Before marking non-normative, re-read the section sentence by sentence. The mark and the goal justification account for each normative sentence by the requirement id that carries it: a justification claiming an extraction names an id staged in this session or already recorded, and claiming a sentence extracted while staging nothing for it is a dishonest mark. Three reasons are always wrong and are rejected: "it states a fact, not a requirement", "it describes content or appearance, not behavior", "it is not a requirement on the system".

Record the facts as stated, even when sections disagree: judging contradictions and duplicates belongs to the judgment goals that follow, and a conflict you notice is not lost.
