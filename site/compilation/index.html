Compilation is reconciliation

The documents are desired state, the graph is observed state

A build compares the two and derives goals until they agree. Everything that must never be wrong is deterministic code; the model is invoked only inside bounded sessions, behind validation gates. The first build is not a special case: it reconciles against an empty graph. A rebuild with nothing changed derives zero goals and makes zero LLM calls.

parse the documents → diff section trees → dirty set
  → derive the goal board  (from the docs, the graph, the ledger, the change records)
  → compile sessions       (highest ready tier first: alignment, ingest, judgment)
  → GC bursts              (a settled cone at a time: edges, duplicates, views, levels)
  → checks                 (coverage, reachability, provenance, level shape, ...)
  → converged, or incomplete with the work parked and named

The steps

  1. Parse deterministic

    Each document becomes a section tree with verbatim text and per-section content hashes. A PlantUML block in a document is input too, parsed as a diagram section.

  2. Diff deterministic

    The section diff is the sole source of staleness. Changed and removed sections are dirty; a section that merely moved has its anchors rewritten mechanically and stays clean. The model never decides what is stale.

  3. Derive goals deterministic

    The board is never stored: it is derived from the documents, the graph, and the change records earlier commits left behind. A goal is one kind on one target, g:reconcile-section:docs/checkout.md#/checkout, with the committed mutation that opened it as its cause. Compile goals bring the graph in line with the documents; GC goals restructure it once a limit is crossed, optional past the soft threshold and mandatory past the hard one. Readiness tiers order the compile goals, and a GC goal is ready only when no compile goal is open in its target's cone.

  4. Compile sessions LLM

    One session per batch of ready goals, grouped by locality and filled to a context budget. The prompt is assembled from fixed payload files, never authored per goal. The model loads the graph explicitly, reads the dirty sections, searches before creating any entity, records requirements with verbatim quotes, declares edges, marks each section covered or non-normative, and justifies each goal it marks done. Mutations are staged, validated one by one, and committed atomically when the session finishes.

  5. Judgment and GC LLM

    A mutation opens the goals that judge it: a pair of requirements to re-judge for contradiction or duplication, an entity to review as a whole. When a neighborhood settles, GC bursts restructure it: declare the edges a statement implies, merge lookalikes, curate or split an over-limit view, and group a level whose children crossed the limit. The model names and judges; the harness counts.

  6. Checks deterministic

    Whole-graph lint: sections left unprocessed, unreachable entities, quotes that no longer locate, coverage claims that dodge normative text, containment and conformance, state machines, and the level shape: every node with children has its level view, none is over the hard fan-out, and no grouping has fewer than two members.

  7. Fixed point deterministic

    The build converges when no mandatory goal is open or failed and the checks are clean. Goals that block on a human (a contradiction to answer, a proposal to ratify) ride beside the verdict as a count. Work that exhausts its budget parks with the reason; the next build resumes it first. Nothing fails silently.

A GC burst, as it runs

A limit is a registry constant, never a project setting. When one flat glossary states eleven concepts under Checkout, the harness opens a fan-out goal on it and computes which children belong together from the requirements that mention them and the relationships between them; the model names the groupings from the documents, or declines with a reason when the level is genuinely flat. The session's changeset as the journal recorded it, condensed to one of the three groupings:

# jazyk-out/journal/g20.yaml
batch:
- g:abstract-entity:ent:checkout
mutations:
- op: create_entity
  id: ent:funds
  entity:
    name: Funds
    definition: 'Funds gathers the balances and methods a customer spends
      at Checkout: the Gift Card, the Loyalty Point, and the Payment Method.'
    parent: ent:checkout
    provenance:
      derived:
        from: [ent:gift-card, ent:loyalty-point, ent:payment-method]
        reasoning: The documents name a payment cluster of the gift card,
          the loyalty point, and the payment method; each is a balance or
          method a customer spends at Checkout, so a reader would recognize
          them as one area. The name "Payment" is taken by a different
          concept (ent:payment, which settles an Invoice and is not a child
          of Checkout), so this area is named "Funds". ...
- op: update_entity
  id: ent:gift-card
  parent: ent:funds
  prior: {parent: ent:checkout}
...
resolved_goals:
- goal: g:abstract-entity:ent:checkout
  justification: Checkout's 11 direct children are grouped into three
    derived groupings under it ... reducing the level to 5 children (≤9).
    The harness files a ratification proposal per derived grouping; Address
    and Receipt stay ungrouped as they share no nameable noun.
rounds: 7

Each grouping carries a proposal for the sentence the documents should gain; the owner accepts it into the document or retracts it. The levels page walks the result.

Gates, not hope

Every mutation the model stages is validated at staging. A rejection names the rule and how to repair the call, because the caller is a model that will read it and try again:

✗ unknown-id: unknown entity id `ent:Product`; nearest existing:
  ent:product; use one of those, or create it with upsert_entity first

✗ junk-name: `--api-key` looks like a CLI flag; entities are domain
  concepts. If it truly is one, repeat the call with a note explaining why

✗ quote-not-found: quote not found in docs/admin.md#/admin-cli/rules;
  copy the sentence verbatim from the section

✗ stated-entity: dissolve_entity on an entity a document states;
  revise the documents instead

Identity never depends on the model. Ids are minted by the store at creation and never change; creates key on the entity's name, so a retried create lands on the existing node instead of duplicating it. A merge leaves a redirect, a dissolved grouping leaves a tombstone, and anything holding the old id still resolves.
