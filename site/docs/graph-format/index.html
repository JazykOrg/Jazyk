SEMANTIC GRAPH

Graph YAML format

Record fields, IDs, references, and provenance in the graph shards.

On this page

ID-keyed YAML maps

Each node type is stored in its own YAML file (a shard), mapping node ID to record. The ID is the mapping key, not a field inside the record. Field names differ by node type.

Examples use illustrative IDs and source text. Writes are validated against live nodes and located quotes.

Entities: names, containment, and mentions

Example · graph/entities.yaml 
ent:order:
  name: Order
  definition: A customer order placed through Orderly.
  stereotype: class
  mentions:
    - doc: docs/orders.md
      section: /orders
      quote: An Order records the customer and placement date.
  created: g12
  updated: g12

name identifies the concept to a reader. aliases records other names. parent is an entity ID for containment. attributes holds typed or valued attributes, each with provenance. mentions locates the concept in prose.

An entity with no authored mention can instead carry derived or decreed provenance. Renaming the entity preserves its ID.

Requirements: statements, edges, and transitions

Example · graph/requirements.yaml 
req:orders-1:
  statement: An unpaid Order becomes cancelled at the start of day 22.
  entities: [ent:order]
  transition:
    subject: ent:order
    from: placed
    to: cancelled
    trigger: start of day 22 after placement
    guard: the Order is unpaid
  facets:
    - facet: behavior
      reasoning: The Order changes state under a stated condition.
  source:
    doc: docs/orders.md
    section: /orders/cancellation
    quote: An unpaid Order becomes cancelled at the start of day 22.
  created: g12
  updated: g12

statement is the obligation as the model restates it. source.quote remains verbatim. A requirement has exactly one of source or provenance.

Excerpt · edges on a different requirement 
edges:
  - a: ent:checkout
    b: ent:inventory
    type: dependency
    cardinality: "1"

An edge is directional from a to b. Both endpoints must be in that requirement’s entities. A missing edge type contributes a dependency. A transition’s subject must also be in entities.

Criteria: one owner and an observable outcome

Example · graph/criteria.yaml 
crit:orders-1:
  requirement: req:orders-1
  statement: An Order placed on day 0 and unpaid at the start of day 22 is cancelled.
  kind: boundary
  source:
    doc: docs/orders.md
    section: /orders/examples
    quote: An Order placed on day 0 and unpaid at the start of day 22 is cancelled.
  created: g12
  updated: g12

requirement is the single owning requirement ID. Optional given, when, and then split the same condition. A quality criterion can carry a measure. Tests in the ledger are keyed to criterion IDs.

Quoted, derived, and decreed facts

Excerpt · derived provenance 
provenance:
  derived:
    from: [req:orders-1]
    reasoning: The cancellation rule implies a cancelled state.

Derived provenance names upstream IDs and reasoning. Decree provenance names the human author and timestamp, with an optional note. Quote provenance names doc, section, and verbatim quote.

Quote placement is whitespace-insensitive string matching, not a character offset. Requirements and criteria use source for their quote form; entities use mentions; attributes use provenance.

Views, derived records, and diagnostics

Shard Record content
views.yaml kind, title, ordered members, optional query, collapse, exclusions, and provenance. Defaults carry default: true.
relationships.yaml Entity pairs and contributions grouped by direction and type, derived from requirement edges.
state-machines.yaml Subject entity, states, and transitions derived from requirement transitions.
diagnostics.yaml rule, severity, subjects, message, judgment reasoning, lifecycle, and optional prompt, answer, and triage.
redirects.yaml An absorbed node ID mapped to its surviving ID.

Relationships and state machines are rewritten at commit. Their contributions lead back to requirements. A view selects facts for a diagram; it does not store their coordinates.

IDs and set scope

Prefixes identify node kinds: ent:, req:, crit:, view:, rel:, sm:, and diag:. The same local ID can exist in different set stores.

On disk, records use local IDs. Cross-set API results qualify them, e.g. req:ds_main::orders-1. CLI graph operations use --set to disambiguate scope. created and updated are generation markers such as g12.

Use compiler tools for validated edits. YAML readability makes records inspectable; a text edit does not provide the provenance, gates, and journal work of a changeset.
