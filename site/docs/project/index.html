Directory layout

The project-wide files live directly in .jazyk/. Each named document set has its own store at .jazyk/<set-id>/. Source documents and product files stay at the paths selected in configuration.

Native project layout · representative set 
.jazyk/
  jazyk.toml                 Project configuration (TOML)
  .gitignore                 Generated-state ignore rules
  project.lock               Project operation coordination
  sessions/                  Project-wide conversations
  runs/                      Grouped jobs
  removed-sets/              Retained set definitions
  ds_main/                   One document set
    graph/
      entities.yaml
      requirements.yaml
      criteria.yaml
      views.yaml
      diagnostics.yaml
      redirects.yaml
      relationships.yaml
      state-machines.yaml
    docs/                    Mirrored document records
    status.yaml              Store version, generation, verdict, work, costs
    journal/g12.yaml         One committed generation
    gen/ledger.yaml          Bindings and verification metadata
    diagrams/<kind>/         PlantUML and SVG projections
    docsgen/                 Generated graph documentation
    trace/                   Build transcripts (JSON Lines)
    sessions/                Worker and chat session records
    control.yaml             Workflow modes and releases
    workers/                 Registered workers
    leases/                  Claimed work
    .lock                    Store writer coordination

Directories appear as their features are used. This is the native filesystem layout. A Cloud project is persisted by the hosted service; it is not a directory mounted on your computer.

graph/: semantic records

Files Purpose
entities.yaml, requirements.yaml, criteria.yaml The named subjects, their obligations, and observable criteria.
views.yaml Curated views and derived defaults.
diagnostics.yaml Persistent judgments, questions, answers, and triage.
redirects.yaml Identity redirects left by merges.
relationships.yaml, state-machines.yaml Derived from requirement edges and transitions on each commit.

Each shard is an ID-keyed YAML map. See Graph YAML format for fields and examples. The ledger is outside these shards.

docs/: parsed source and coverage

A source such as docs/orders.md is mirrored at .jazyk/ds_main/docs/docs/orders.md.yaml for the ds_main set. The source-relative path is preserved beneath the store’s docs/ directory. The record stores its last content hash, section tree, and coverage marks.

Excerpt · illustrative document record, hashes omitted 
contentHash: "<source content hash>"
sections:
  /orders/cancellation:
    title: Cancellation
    kind: heading
    order: 0
    parent: /orders
    raw: |-
      ## Cancellation

      An unpaid Order becomes cancelled at the start of day 22.
    hash: "<section hash>"
    lines: [4, 7]
coverage:
  /orders/cancellation:
    state: covered
    note: The cancellation obligation is recorded.
    claimedBy: [req:orders-1]

The field is contentHash, with that casing. Section references are heading paths. raw preserves source text; lines locates it for editors. Coverage is unprocessed, covered, or non-normative. It describes section reconciliation, not test success.

status.yaml: the current store state

Excerpt · status.yaml 
version: 2
generation: 12
verdict:
  state: converged
  open: 0
  failed: 0
  blocked: 1
  optional: 0

version is the store schema version. It is separate from config version = 1. generation advances on commit. The verdict includes blocked and optional work even when mandatory work converged.

Other fields include changes, parked, failed, costs, spent, diagnostic counts, and alignment records. The board derives live goals from these records; it is not a standalone goals.yaml file.

journal/: committed changes

g12.yaml records generation 12. Entries carry kind, mutations, opened_goals, resolved_goals, session rounds, and available token usage. Resolutions include their justification.

A document save records the sections it dirtied. A session records its graph changes and goal outcomes. Use jazyk ripple to follow these causes rather than treating a transcript as the authoritative change history.

gen/ledger.yaml: files, tests, and evidence

The ledger links graph requirements to product files and criteria to tests. It has entity-generation and requirement-binding maps, plus medium, build, and support-file metadata.

Excerpt · illustrative ledger binding 
requirements:
  req:orders-1:
    entity: ent:order
    files: [src/orders.rs]
    tests:
      crit:orders-1:
        kind: programmatic
        label: unit
        artifact: tests/orders.rs
        name: crit_orders_1_a1b2c3d4
        run: cargo test crit_orders_1_a1b2c3d4
        cwd: .
        verdict: none

Rows also record hashes, implementing sites, last-run data, and evidence. Status is derived from that data and current artifact bytes. A stored pass whose inputs changed is stale. jazyk test --audit rebuilds bindings from artifact markers without running tests.

Renderings, transcripts, and runtime files

Path Format and use
diagrams/ .puml and .svg per view; .png on demand. Regenerable projections.
docsgen/ Generated Markdown pages for requirements, entities, levels, and diagrams.
trace/ JSON Lines: run metadata, numbered trace events, and final outcome when recorded.
sessions/ Conversation and session records. These are distinct from graph commits.
control.yaml Manual or automatic modes and standing releases.
workers/, leases/, locks Coordination for active workers and writers, not authored requirements.

What to track and what to preserve

Track authored docs, product source, .jazyk/jazyk.toml, and .jazyk/.gitignore. Keep generated set state and secrets ignored. See configuration and Git rules.

Ignoring graph state in Git does not make it disposable. Deleting renderings loses no semantic facts. Deleting a set’s store discards its IDs, judgments, history, and local evidence. A rebuild may extract another graph, but it does not restore that record.

A store-version mismatch archives the set store before a build starts from empty. It does not migrate the old graph or replace project configuration.
