Give the subject a home.

Organize documents so both a person and the compiler can follow what they describe.

Organize around the subject

A document set is a collection of documents about one subject. It may describe an application, a department, a story, or a deck. Headings divide that subject into sections the compiler can reconcile.

Start with a front door that names the subject and links to its parts. Give each part a stable home. Split a file when a reader needs a focused explanation, not to meet a word count.

Example · document layout 
docs/
  main.md           What Orderly is, and links to its parts
  orders.md         Order lifecycle and cancellation rules
  payments.md       Payment behavior and failure cases
  examples.md       Concrete cases with expected outcomes

Jazyk does not require these names or this folder. The chosen set’s patterns determine input.

Use headings and links as structure

Example · docs/main.md 
# Orderly

Orderly accepts customer Orders and records their Payments.

- [Order lifecycle](./orders.md)
- [Payments](./payments.md)
- [Examples](./examples.md)

Headings create a section tree. Body text before the first heading is read too. Lists and blockquotes stay in the surrounding section. Ordinary fenced code is read in that context; a PlantUML fence is a diagram input section.

Relative document links connect the reading order and help the compiler ingest foundational documents first. Configure roots as entry points. A heading groups text; it does not automatically create an entity with that heading’s name.

Choose the right document-set boundary

Use one set for a coherent subject. Use separate sets for separate models, such as an application and its operating organization. Each has independent identities, graph, diagnostics, and history.

Files can belong to several sets, but each set compiles them separately. Shared input is deliberate duplication of work, not one shared graph. Review overlaps when selecting paths.

Terminal 
jazyk sets add Main --docs 'docs/**/*.md' --roots docs/main.md

Quote shell patterns. Use exclusions for documents you do not want compiled, such as archival notes or model instruction payloads.

Keep documents and source files distinct

Role Purpose Example
Documents State what the subject must be or do. docs/orders.md
Source The implementation or artifact files the set describes and may generate. src/**, slides/**
Compiler state Persistent graph, judgments, diagrams, history, and evidence metadata. .jazyk/<set-id>/

Selecting source files does not prove which requirement they implement. Binding records that evidence. Files selected as docs cannot be generation write targets, even if a broad source pattern also matches them.

Pick an input format you can maintain

Markdown is the simplest portable choice. Native builds also read plain text, DOCX, and PDF within their extraction profiles. The browser-only engine currently reads Markdown.

Keep one obvious title and meaningful section headings. A PDF’s reading order and extracted text may need inspection. Unsupported or unreadable inputs produce diagnostics rather than silently becoming a successful compile.
