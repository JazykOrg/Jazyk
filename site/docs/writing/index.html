LEARN THE COMPILER

Write what you mean.

Clear subjects, explicit obligations, and concrete examples give the compiler something you can judge.

On this page

State what must be true

You do not need a special grammar or the word “shall.” A declarative sentence about the subject states an obligation. What a slide shows, what a service allows, and what a department owns can all be requirements.

Vague prose More useful prose
Orders expire eventually. Orderly cancels an unpaid Order at the start of day 22 after placement.
Only authorized people can change things. Only an Admin can change an Order’s delivery address after payment.
The slide should look good. The Introduction slide shows the title “Jazyk” and a link to jazyk.org.
Search is fast. For 10,000 Orders and 20 concurrent readers, search responds within 200 ms at the 95th percentile over a 5-minute run.

These are illustrative revisions. Choose values because they are your requirements. Do not add arbitrary numbers just to make a sentence measurable. If you have not decided a threshold, state the open question.

Name subjects consistently

Introduce the real subject and its parts. Prefer “Orderly cancels the Order” when “it cancels it” could refer to several things. Keep a term stable across documents; if two names mean the same thing, say so.

Name scope when a word is reused. Two modules can each have a Config without being the same entity. A relationship also needs direction: who sends, owns, contains, or depends on what?

Keep separable obligations easy to see. “The gateway uses Go and exposes REST” carries two constraints that can fail independently.

Write criteria as concrete examples

Example · author-written prose 
## Cancellation

Orderly cancels an unpaid Order at the start of day 22 after placement.

## Examples

An Order placed on day 0 and still unpaid on day 21 remains placed.
An Order placed on day 0 and still unpaid at the start of day 22 is cancelled.
An Order paid on day 5 is not cancelled for non-payment.

The rule states intent. The examples make it observable. Include the successful case, the failure case, and the boundary. A useful criterion has one condition and one outcome with the values intact.

“The Order follows the cancellation rule” repeats the requirement. It does not say how to tell whether the rule is met. Avoid naming an internal function unless that interface itself is a constraint.

Describe the artifact as well as behavior

For a deck, name the audience, slide content, file format, and constraints that matter. For a manuscript, state viewpoint, chapter obligations, and any length bounds. For software, state relevant interfaces, data, permissions, states, and failure behavior.

If a toolchain, language, or format matters, write it down. If it is free to vary, leave that choice open and review what generation proposes.

The artifact is the thing you asked for

A requirement for a PowerPoint deck means a deck, with its required content. A Markdown description saying that a deck should exist is not that deliverable.

Review your prose before expanding it

  • Can a reader identify the subject of each obligation?
  • Do two sections disagree about the same condition?
  • Are thresholds, exceptions, and permissions explicit where they matter?
  • Do examples prove outcomes rather than repeat the rule?
  • Is old history clearly separate from current obligations?
  • Does the requested medium match the artifact you expect?

Compile one focused set and inspect what it understood. Fix the prose where the meaning is wrong. More text is useful only when it resolves something.
