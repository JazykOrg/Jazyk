The graph

The build artifact is a persistent semantic graph, not a report

Three authored kinds, two derived

Sections carry the documents' structure. Entities, requirements, and views are authored by sessions and by humans; relationships and state machines are recomputed from them on every commit. Diagnostics are the compiler's sticky judgment records. Nodes are created once and edited in place across builds: a rename keeps the id, a merge leaves a redirect, a dissolved grouping leaves a tombstone, and a cleared finding resolves instead of vanishing.

Section

Document structure as a parent and child tree. Holds the verbatim text; every quote locates inside it, whitespace-insensitively, never by character offset.

Entity

A domain concept with one living definition, a stereotype, attributes, and one parent: the containment tree that levels are built from. One concept, one node, never a per-document copy.

Requirement

A free-form statement restating what a sentence obliges, attached to entities, with the verbatim source sentence as its quote, directional edges, an optional transition, and facets.

View

What one diagram includes: kind, title, members, a query, collapses, exclusions. Never how it looks. Default views derive per level, per flow cluster, per machine; a curated view is authored.

Relationship derived

One node per pair of entities, the contributing edges grouped by direction and type. No requirement, no edge.

State machine derived

One per subject entity, from the transitions its requirements carry. A state that no transition leaves is a check finding, not a picture.

Diagnostic

A recorded judgment: contradiction, ambiguity, duplicate, uncovered section, a proposal awaiting ratification. Sticky by construction: it keeps its id across builds, and a human triage mark is never overwritten by the compiler. A diagnostic with a prompt is a question the owner answers, each option an exact edit to a document.

Provenance

Every fact has exactly one provenance. A quote is a verbatim sentence in a section. A derived fact names the nodes it came from and the reasoning. A decree is a human write on the graph. Derived and decreed facts carry a proposal for the sentence the documents should gain; accepting it writes the sentence and flips the provenance to a quote, so the graph converges toward fully quoted.

On disk

Plain YAML, sorted for clean diffs, under jazyk-out/: one shard per node kind, one file per document's section tree and coverage, a journal entry per committed changeset, the diagrams, the generated pages, and a status file with the convergence verdict. One entity, one requirement, and one view, verbatim from a real build:

# graph/entities.yaml
ent:gift-card:
  name: Gift Card
  definition: A Gift Card is a prepaid balance a customer spends at Checkout.
  stereotype: entity
  parent: ent:funds
  mentions:
  - doc: docs/checkout.md
    section: /checkout
    quote: A Gift Card is a prepaid balance a customer spends at Checkout.
  - doc: docs/checkout.md
    section: /checkout/rules
    quote: A Gift Card shall never be charged beyond its balance.
  created: g16
  updated: g20      # reparented under the Funds grouping

# graph/requirements.yaml
req:checkout-8:
  statement: A Checkout turns a Cart into an Order.
  entities:
  - ent:checkout
  - ent:cart
  - ent:order
  edges:
  - a: ent:checkout
    b: ent:cart
    type: association
  - a: ent:checkout
    b: ent:order
    type: association
  facets:
  - facet: behavior
    reasoning: A Checkout turns a Cart into an Order.
  source:
    doc: docs/checkout.md
    section: /checkout
    quote: A Checkout turns a Cart into an Order.
  created: g11
  updated: g11

Ids are minted by the store at creation and never change, so generated code, tests, tickets, and cards bind to ent:checkout and stay bound through renames, merges, and reparents. The journal records every changeset with each goal's justification: the audit trail explains the graph, not just describes it.

A view and its diagram

A view stores what a diagram includes, never how it looks. This one is the level view of Checkout, derived on every commit from its direct children plus the outside entities their edges reach; the renderer lifts every edge that touches a hidden descendant to the member that contains it and draws the picture on the right.

# graph/views.yaml
view:class/checkout:
  kind: class
  title: Checkout
  members:
  - ent:address
  - ent:receipt
  - ent:funds
  - ent:pricing
  - ent:selection
  - ent:order
  - ent:payment
  provenance:
    derived:
      from:
      - ent:checkout
      - ent:address
      - ent:receipt
      - ent:funds
      - ent:pricing
      - ent:selection
      - ent:order
      - ent:payment
      reasoning: 'default view: level view
        of a node'
  default: true
  created: g13
  updated: g20

diagrams/class/checkout.svg. Funds, Pricing, and Selection hold levels of their own; the levels page digs in.

Queryable, the same way, everywhere

One loaded set serves every reader: a target in full, its edges, each neighbor as a stub, and a handle for whatever the budget cut off. A session loads the graph through it, and so do the CLI, the MCP server, the language server, and the GUI, so an agent asking about ent:funds sees exactly what the compiler saw.
