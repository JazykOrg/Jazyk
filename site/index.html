Jazyk /ˈjazɪk/

Compiler for natural language

Input
Documentation

Loose prose: requirements, product use cases, design pages. The compiler does not constrain the English you write.

Process
Reconciliation

A deterministic harness finds what changed and derives goals from it; bounded LLM sessions resolve the goals, one batch at a time, behind validation gates.

Output
The semantic graph

Entities in one containment tree, requirement statements with verbatim quotes, views, derived relationships and state machines, sticky diagnostics. Persistent, edited in place, never regenerated. Every UML diagram renders from it.

Control
  • CLI to compile, watch, query, and answer
  • MCP so agents read the same graph through the same tools
  • IDE via the Language Server Protocol: hover an entity, see its card
  • GUI with the containment tree, the diagrams, and the questions the build asks
Usages
  • Diagrams: every UML kind, one set per level, drill-down between them
  • Code generation: one unit per entity, every requirement verified by a real test run
  • Documentation: a card per entity, a page per diagram, a walk
  • Model benchmark: grades whether a model can drive compilation

The thesis

Open-ended prompts to a model are unreliable; small, well-defined ones are not. Jazyk decomposes loose documentation into many small, well-defined units, entities and the requirement statements attached to them, so everything downstream operates in the reliable regime.

The graph, not the prose, is the build artifact. It persists across builds: nodes are created once and edited in place, ids never change, and human triage on a finding survives every rebuild. Every fact carries its provenance: a verbatim quote, a derivation from upstream facts, or a human decree. Downstream tools bind to entity ids and stay bound.

A session, as it runs

Compilation is model-driven but harness-governed. The harness derives goals from what changed and hands a session a batch of them. The model reads the dirty sections, searches the graph before creating anything, and stages mutations that commit only if every validation gate passes; each staged mutation previews the goals it will open. From a real trace, condensed:

[b10-1] g:reconcile-section:docs/checkout.md#/checkout, #/checkout/rules
→ read_section {"ref":"docs/checkout.md#/checkout"}
→ search {"query":"Checkout"}
← {"hits":[],"entityCount":16, ...}
→ upsert_entity {"name":"Checkout","stereotype":"process",
   "definition":"A Checkout turns a Cart into an Order.",
   "mention":{"quote":"A Checkout turns a Cart into an Order.",
              "section":"docs/checkout.md#/checkout"}}
← {"id":"ent:checkout","created":true,
   "opens":["abstract-entity scope:public (fan-out 12 over soft 9, optional)"]}
→ upsert_requirement {"statement":"A Checkout turns a Cart into an Order.",
   "quote":"A Checkout turns a Cart into an Order.",
   "entities":["ent:checkout","ent:cart","ent:order"],
   "edges":[{"a":"ent:checkout","b":"ent:cart","type":"association"}, ...]}
← {"id":"req:checkout-8","created":true,
   "opens":["review-entity ent:checkout (requirements changed)", ...]}
→ set_coverage {"section":"docs/checkout.md#/checkout","state":"covered", ...}
→ mark_goal_done {"goal":"g:reconcile-section:docs/checkout.md#/checkout",
   "justification":"The /checkout section's eight definition sentences each
   state what a domain part is or does and are extracted as req:checkout-1
   through req:checkout-8 ..."}
→ done
← {"committed":true,"generation":11,"applied":24,
   "opened":["g:abstract-entity:scope:public","g:review-entity:ent:checkout", ...]}

Changes stay small

A rebuild with nothing changed derives zero goals and makes zero LLM calls. Editing one sentence dirties one section: one goal reconciles it, the mutations it stages open the judgment goals on the touched entities and pairs, and the graph diff is additive. Contradictions across documents surface as sticky diagnostics with the compiler's reasoning attached and a question the owner answers, each option an exact edit to a document.

diag:contradiction-1  error  [req:orders-4, req:payment-3]
  Payment deadline conflict: orders says "An Order shall be paid within 21
  days of placement; otherwise the system shall cancel it." while payment
  says "An Order shall be paid within 30 days of placement."
  Should the Order payment deadline be 21 days or 30 days?
  0  Use 21 days in payment rules (edit docs/payment.md /payment/rules)
  1  Use 30 days in order lifecycle (edit docs/orders.md /order/lifecycle)

Levels

Requirements stay on the entities the documents state. Those entities summarize into groupings, and those into higher still, under a children limit the harness enforces and a name the model chooses from the documents. Every level gets its own structural, use case, and sequence diagrams, and digging into an entity shows the level below it. A grouping no document states carries a proposal for the sentence the documents should gain: the compiler proposes the architecture chapter the documents never wrote, and the owner accepts or retracts it.

The top level of a real build: five boxes over thirty-two entities four levels deep. The line between Checkout and Orders stands for four sentences, one of them "A Checkout turns a Cart into an Order." Dig in.
